### 핵심 로직이 왜 그렇게 동작하나

**1. 밸런스 수치를 데이터 클래스로 만들지 않고 "경로로 읽게" 했다.**
`balance.json` 은 마일스톤마다 항목이 늘고 모양도 바뀐다. 매번 데이터 클래스를 고치면 작업이 늘고,
필드를 빠뜨리면 조용히 기본값이 쓰인다. 그래서 `balance.double("injury.severityShare.minor")` 처럼
경로로 읽는다. 대신 **값이 없거나 타입이 다르면 그 자리에서 예외를 던진다.** 밸런스가 말없이 달라지는
상황(불변 원칙 3이 진짜 막으려는 것)을 막기 위해서다. `intRange("injury.durationWeeks.minor")`,
`numericMap("ratingTables.batterContactToK")`(능력치 앵커표), `sections("softCap.penalties")`
같은 전용 읽기 함수를 함께 두어 호출부가 JSON 구조를 직접 다루지 않게 했다.

**2. 엔진은 파일을 읽지 않는다.**
`BalanceConfig.parse(text)` 는 문자열만 받는다. 파일을 찾아 읽는 일은 JVM 쪽 `ProjectFiles` 가 한다.
불변 원칙 1(엔진에 플랫폼 API 없음)을 M0부터 구조로 못박아 두면, 나중에 Android/iOS 를 붙일 때
엔진을 건드릴 일이 없다. 저장소 루트는 `-Dbaseballgm.root` 로 받고, 없으면 현재 폴더에서 위로 올라가며
`config/balance.json` + `data/teams.json` 이 같이 있는 폴더를 찾는다.

**3. `teams.json` 의 `generation` 은 팀마다 키가 다르다.**
(대성 나이츠는 `earlyGrowthBias`, 수원 로얄스는 `balanced` …) 전부 nullable 필드로 만들면 의미 없는
필드가 잔뜩 생긴다. 그래서 `generation` 은 JSON 그대로 두고 `team.generationHints.doubleOrNull("…")`
로 읽는다. M1 리그 생성기가 팀별로 필요한 힌트만 꺼내 쓰면 된다.

**4. `teams.json` 자체 검산(`validate()`).**
리그 생성기가 잘못된 목표치를 그대로 믿고 선수를 만드는 사고를 막으려고, 데이터가 앞뒤가 맞는지 먼저 본다.
구단 10개인지 · ID 중복 없는지 · 지명 순번이 1~10 순열인지 · 튜토리얼 추천 구단이 정확히 1개인지 ·
`overall` 이 타선/선발/불펜 가중 평균(0.45/0.35/0.20)과 1점 이내인지 등. 현재 데이터는 전부 통과한다
(10팀 모두 가중 평균과 0.5점 이내).

### 2. 핵심 로직이 왜 그렇게 동작하나

**(1) 선수는 거꾸로 만든다 — 잠재력 → 나이 → 현재 능력치**

능력치를 먼저 뽑고 나이를 붙이면 "23세인데 이미 전성기" 같은 선수가 생긴다. 그래서 docs/03 순서대로
① 잠재력을 뽑고 ② 유형·포지션 편향으로 *모양*을 만들고 ③ 나이·성장 타입으로 현재치를 역산한다.

역산 식은 docs/09 곡선 그대로다. 데뷔 시점 능력치(잠재력의 45~72%, 고졸이 더 낮다)에서 출발해
전성기 시작 나이까지 매년 (잠재력 − 현재)의 20~35%를 좁히고, 전성기가 지난 햇수만큼 깎는다.
**능력치마다 속도가 다르다**: 파워·제구는 늦게까지 오르고(성장 배율 1.25/1.2), 주루·수비는 빨리
떨어진다(하락 배율 1.7/1.4). 그래서 34세 유격수는 수비·주루가 먼저 무너지고 선구안은 남는,
"1루로 옮길 때가 된 선수"가 저절로 만들어진다. 노화 곡선 코드를 M5 에서 다시 쓸 수 있도록
같은 설정값(`aging`, `attributeGrowthSpeed`)을 읽는다.

유형 편향(거포 파워 +13 등)은 더한 뒤 **종합이 목표치가 되도록 전체를 평행 이동**한다.
유형은 모양만 정하고 수준은 팀 목표가 정한다는 뜻이다.

**(2) 팀 전력 맞추기는 재시도가 아니라 되먹임**

"±2 안 나오면 다시 뽑기"를 하면 운에 기대게 되고 팀 성격(나이·계약)이 흔들린다. 대신
① 한 번 만들고 → ② 목표와의 차이를 재고 → ③ 그 차이만큼 잠재력 평균을 옮겨 **같은 난수열로**
다시 만든다. 난수열이 같으니 바뀌는 건 능력치 수준뿐이고, 보통 **2~3번 만에** 수렴한다.
(처음 25번은 같은 난수열, 그래도 안 맞으면 난수열을 바꾼다)

**(3) 팀 전력 스케일 ≠ 선수 능력치 스케일** — 처음에 틀렸다가 고친 부분

`teams.json` 의 전력 82를 "주전 평균 능력치 82"로 해석했더니 컨택 97 같은 선수가 쏟아졌다.
docs/02 는 주전 평균을 60으로, docs/01 은 팀 전력을 40~90 분포로 정의한다. **둘은 다른 자다.**
그래서 `teamStrength.ratingToStrength`(pivot 50, slope 1.6) 변환을 넣었다:
`전력 = 50 + (능력치 평균 − 50) × 1.6`. 이 변환 뒤 주전 평균이 60.4로 떨어지고 90+ 능력치가
리그 전체 2개로 줄었다(docs/02 "90 이상은 손에 꼽을 정도"). 되먹임도 전력 차이를 1.6 으로 나눠
능력치 차이로 바꿔서 적용한다 — 안 그러면 1.6배 과잉 교정으로 진동한다.

**(4) 숨김 수치는 컴파일 단계에서 막았다 (불변 원칙 4)**

`HiddenTraits` 의 모든 프로퍼티를 `internal` 로 뒀다. 생성기는 값을 **넣을 수만** 있고(생성자는 공개),
읽지는 못한다. 확인해 봤다 — `cli` 에서 `player.hidden.durability` 를 쓰면 빌드가 깨진다:
`Cannot access 'val durability': it is internal`. `data class` 를 쓰지 않은 이유도 같다.
자동 생성 `toString` 이 잠재력을 그대로 찍어버리기 때문에, `toString` 은 `HiddenTraits(숨김)` 으로
막고 `equals`/`hashCode` 만 손으로 구현했다.

스카우트 오차는 **선수마다 고정**이다. 선수가 가진 `scoutingNoiseSeed` 로 오차를 계산하므로
같은 선수를 100번 열어도 같은 범위가 나온다(여러 번 열어 평균 내는 꼼수 차단). 오차는 범위의
중심 자체를 밀어서 **진짜 값이 한가운데 오지 않는다**. 성장 타입 추정은 정확도가 낮으면 틀린다.

**(5) 일정표는 원형 스케줄(circle method)로 만든다**

숫자가 정확히 맞아떨어진다. 10팀 → 9라운드 한 바퀴가 45개 조합을 한 번씩 덮는다.
- 3연전: 한 바퀴 = 조합당 1시리즈. **네 바퀴 = 36슬롯**, 한 주에 2슬롯(화~목, 금~일) → **18주**
- 2연전: **두 바퀴 = 18슬롯**, 한 주에 3슬롯(화수·목금·토일) → **6주** (시즌 후반 배치)
- 합쳐서 24주 × 6경기 = 144경기, 상대별 16경기 ✓

홈·원정은 바퀴마다 뒤집는다. 그러면 3연전에서 6홈 6원정, 2연전에서 2홈 2원정 → **맞대결 8:8** 이 정확히 맞는다.
한 주 안에서는 서로 다른 라운드만 묶어서 같은 상대를 한 주에 두 번 만나지 않게 했다.

**(6) 연봉은 상대 크기만 만들고 팀 총액에 맞춘다**

선수별 연봉은 종합 능력치 앵커표 × 연차 배율(신인 0.35 / 연봉조정 0.75 / 베테랑 1.0 / FA 1.6)로
정하고, 팀 단위로 비례 조정해 `teams.json` 의 연봉 총액에 맞춘다. 최저 연봉 밑으로 내려가지
않도록 두 번에 나눠 맞춘다. 그래서 10팀 연봉 총액이 목표와 **정확히** 일치한다.

**(7) 구단 성격은 `generation` 힌트로 들어간다**

`starterAvgAgeMin`(나이 이동), `earlyGrowthBias`, `hitterPowerBias`, `under25Share`,
`lowSalaryShare`, `longContractsHeavy`, `overpaidVeteranFaHitters`(악성 계약), `cheapVeteransAge35Plus`,
`farmPotential`/`prospectDepth`/`prospectQuality`/`aGradeProspects`(2군 잠재력), `keyPitchersFaInYears`,
`potentialOverall`, 창원의 외국인 능력치 보너스까지 반영했다.
**다만 `pitcherTargetDelta` 같은 `*TargetDelta` 키는 쓰지 않았다.** 그 성격은 이미 `targets` 값
자체(인천 선발 85)에 들어 있어서 또 더하면 두 번 적용된다.

### 2. 핵심 로직이 왜 그렇게 동작하나

**(1) 타석은 단계별로 좁힌다 (docs/04)**

① 삼진/볼넷/사구/인플레이 → ② 홈런 → ③ 타구 종류 → ④ 안타 여부 → ⑤ 안타 종류 → ⑥ 상황 결과.
각 단계의 확률은 **Log5** 로 합친다. 단순 평균과 달리 리그 평균 선수끼리 붙으면 정확히 리그 평균이
나오고, 극단 매치업에서도 0~1 을 벗어나지 않는다. 능력치는 전부 `ratingTables` 를 거치므로
시뮬레이션 코드에는 숫자가 없다.

⑥에서 **상태에 맞지 않는 결과는 아예 만들지 않는다.** 3루 주자가 없으면 희생플라이가 나올 수 없고,
1루가 비면 병살도 없다. 확률표에서 지우고 가장 가까운 결과(뜬공 아웃, 땅볼 아웃)로 대체한다.

**(2) 자책점은 "가상 아웃" 으로 센다 (docs/05)**

이닝마다 "실책이 없었다면 잡혔을 아웃" 카운터를 따로 돌린다. 실제 아웃에 더해, 실책으로 출루가
생기면 가상 아웃을 하나 더 센다. 어떤 득점이 자책인지는 두 가지로 판정한다:
① 그 주자가 실책으로 나갔으면 비자책, ② 가상 아웃이 이미 3개면 그 뒤 득점은 전부 비자책.
그래서 "실책만 없었으면 이닝이 끝났을 상황"의 실점이 투수 기록에 남지 않는다.

**(3) 책임 투수는 주자가 들고 다닌다**

주자 객체(`Runner`)가 자기를 내보낸 투수 id 를 들고 있다. 투수가 바뀐 뒤 그 주자가 들어오면
앞 투수의 실점이 된다. 베이스 상태를 비트만으로 표현했다면 불가능한 판정이라, 처음부터
베이스마다 주자 객체를 저장하도록 만들었다.

**(4) 주자 보존 불변식 — 여기서 실제 버그를 잡았다**

모든 주자는 **득점했거나, 아웃됐거나, 베이스에 남아 있어야 한다.** 이걸 테스트로 5000번 돌리고
(모든 타석 결과 × 모든 베이스·아웃 조합), 경기마다 박스스코어 등식으로 다시 확인한다.

1,000경기 테스트에서 **한 이닝에 아웃이 4개** 나오는 경기가 걸렸다. 2아웃에서 단타가 터졌을 때
2루 주자와 1루 주자가 **둘 다** 무리한 진루를 하다 죽으면서 아웃이 4개가 된 것이다. 실제 야구에서는
세 번째 아웃이 나오는 순간 플레이가 끝나므로, 아웃이 3개가 되면 뒤 주자는 있던 자리에 멈추도록 고쳤다.
등식 검증이 없었으면 몇백 경기 뒤 이상한 이닝 기록으로나 드러났을 버그다.

**(5) 검증기 자체를 검증한다**

"항상 통과하는 검증기"는 없느니만 못하다. 그래서 일부러 등식을 깬 박스스코어(타석 수가 안 맞는 타자,
사라진 주자, 아웃 26개, 자책 > 실점, 무승부인데 승리 투수)를 넣어 **잡히는지** 테스트한다.

**(6) 승·패·세이브·홀드 (docs/05)**

리드가 바뀌는 순간을 추적한다. 그 시점에 마운드에 있던(=가장 최근에 던진) 투수가 승리 투수 후보,
그 점수의 책임 투수가 패전 후보다. 리드가 다시 바뀌면 후보도 갈린다. 선발이 5이닝을 못 채웠으면
승리는 가장 효과적인 구원 투수(아웃 많고 실점 적은 순)에게 넘어간다. 세이브는 이긴 팀 마지막 투수가
① 3점 차 이내로 등판해 1이닝 이상 ② 동점 주자가 누상에 있을 때 등판 ③ 3이닝 이상 중 하나를
만족할 때 준다. 홀드는 세이브 상황에 등판해 아웃을 잡고 리드를 지킨 중간 투수다.

**(7) 이벤트 스트림 한 갈래 (불변 원칙 5)**

시뮬레이터는 상태를 바꾸면서 `GameEvent` 만 뱉고, 기록·검증·문자 중계(M4)가 그걸 **읽기만** 한다.
관전한 경기와 건너뛴 경기가 같은 코드로 돌기 때문에 "관전하면 결과가 달라지는" 일이 구조적으로 불가능하다.

- **수비는 타구 위치를 따지지 않는다.** 내야 평균/외야 평균 수비력으로 안타 확률과 실책 확률을 정하고,
  실책 기록만 해당 계열 수비수 중 한 명에게 남긴다. 포지션별 타구 분포는 구현하지 않았다(기록 지표에도 없음).
- **대타·대주자·대수비 없음.** M3 규칙표에서 넣는다. 지금은 선발 9명이 끝까지 친다.
- **투수 교체는 임시 규칙**이다 (투구수 한계, 실점 6점, 구원은 1이닝, 9회 3점 차 이내면 마무리).
  `balance.json` 의 `gameFlow` 섹션에 모아 뒀고 M3 에서 규칙표로 대체된다.
- **라인업도 임시**다. 수비 난이도가 높은 자리부터 "수비 적성 + 종합"이 가장 높은 선수를 넣고,
  타순은 1번 출루·주루 / 3~5번 장타의 단순 규칙이다. 좌완용·우완용 두 벌은 M3.
- **난수 도우미를 엔진 `util/` 로 옮겼다.** 시뮬레이션도 정규분포가 필요해서 도구에만 두기 어려웠다.
  (CLAUDE.md §5 패키지 목록에 없는 폴더를 하나 더 추가했다 — `text/` 에 이어 두 번째)
- **낫아웃 출루와 타격방해는 확률을 아주 낮게 넣었다** (`rareEvents`). 드물지만 "출루율 0인데 득점"
  같은 상황을 만드는 출루 방법이라, 주자 보존 등식이 실제로 이 경로까지 검증하도록 넣어 뒀다.
- **좌우 분리 기록의 구조**: 득점·도루처럼 상대 투수의 손과 무관한 기록은 `unsplit` 칸에 따로 쌓는다.
  억지로 우투 칸에 넣으면 "우완 상대 타율" 이 틀어진다. 합계는 `vsLeft + vsRight + unsplit`.

### 2. 핵심 로직이 왜 그렇게 동작하나

**(1) 규칙표는 하나, 채우는 사람만 다르다**

시뮬레이터는 `DirectiveSheet` 만 읽는다. 단장 전용 모드면 감독 AI 가 성향으로 채우고, 감독 겸직이면
유저가 채우고, AI 구단 9개도 같은 구조를 쓴다. **경기 로직에는 "유저 팀"이라는 개념이 없다.**
누가 채웠든 완전히 같은 코드로 돌기 때문에 유저 팀만 유리해지는 일이 구조적으로 불가능하다.

**(2) 감독 성향 → 규칙표 변환은 전부 설정 파일에**

`balance.json` 의 `managerAI` 에 `[성향 1일 때 값, 성향 100일 때 값]` 쌍을 두고 선형 보간한다.
코드에는 "어떤 성향이 어떤 항목을 정하는가"만 있다.

| 성향 | 규칙표 반영 |
|---|---|
| 선발 인내심 | 투구수 한계 88~118구, 실점 한계 4~7, 피로 한계, 세 번째 타순 교체 여부(40 미만) |
| 불펜 혹사 | 연투 2~3일, 최근 7일 80~145구, 필승조 인원 2~4명, 휴식 기준(반대로) |
| 번트 선호 | 번트 슬라이더, 대타를 득점권에서만 쓸지 |
| 도루 적극성 | 도루 슬라이더, 대주자 투입 시점 |
| 플래툰 활용 | 좌우 라인업 가산점 0~14점, 대수비 시점·기준 |
| 유망주 기용 | 25세 이하 라인업 가산점, 대타 시점 |
| 베테랑 신뢰 | 33세 이상 가산점, 대타 교체 기준(높을수록 안 바꿈) |

**(3) 좌완용·우완용 라인업 두 벌**

같은 감독이라도 플래툰 활용 성향이 높으면 두 라인업이 많이 달라진다. 반대 손 타자에게 주는
가산점이 커져서 수비 적성·종합 능력치를 뒤집기 때문이다. 시뮬레이터는 경기 시작 때 **상대 선발의 손**을
보고 한 벌을 고른다. (양타 선수는 항상 반대 손이므로 언제나 가산점을 받는다)

**(4) 불펜은 "역할"로 고른다**

상황 → 역할 → 후보 순서다. 9회 이후 3점 차 이내 리드면 마무리, 8회면 셋업, 6~7회 접전이면 필승조,
후반 접전에 좌타자 차례면 좌완 스페셜리스트, 선발 조기 강판이나 연장이면 롱릴리프, 지고 있으면 추격조.
역할에 적힌 순서대로 "지금 던질 수 있는" 투수를 찾는다.

**(5) 예외 처리 사다리 — 경기는 절대 멈추지 않는다 (docs/06)**

```
① 역할에 맞는 투수 (연투·7일 투구수 제한을 지키는)
② 제한을 지킬 수 있는 아무 투수
③ 추격조
④ 제한 무시하고 아직 안 던진 투수 (PitcherForcedIn 이벤트로 기록 — M4 에서 부상 위험에 반영)
⑤ 그래도 없으면 교체하지 않는다 (지금 투수가 계속 던진다)
```
대타 자원이 없으면 교체 없이 진행한다. **투수를 3명만 남긴 선수단으로 40경기를 돌려** 연장까지 가도
경기가 끝나고 박스스코어 등식이 성립하는지 테스트로 확인한다 (M3 완료 기준).

**(6) 단장 방침은 감독을 반쯤만 움직인다**

단장이 "번트 좀 대라"(20 → 100)고 하면 성향이 100 이 되는 게 아니라 반영률(`managerDirectiveAdoption`,
현재 0.5)만큼인 60 으로 간다. 감독이 캐릭터라는 설정이 수치로 드러나는 부분이다.

**(7) 주간 방침**

총력전은 선발 투구수 한계 ×1.12, 연투 제한 +1일, 휴식 기준 +10, **추격조 앞쪽 2명을 필승조로 승격**한다.
선수 보호는 반대로 조인다. 규칙표를 통째로 다시 만들지 않고 이미 만든 규칙표의 수치만 손보는 구조다.

- **번트 실패**는 선행 주자 아웃(야수선택) 또는 뜬 공(라인아웃)으로 갈린다. 번트 안타 시도는 없다.

### 2. 핵심 로직이 왜 그렇게 동작하나

**(1) 한 주의 흐름 (docs/07)**

```
주 시작 → 엔트리 관리(부상자 말소·콜업) → 규칙표 갱신
   → 화~일 6경기 (경기마다: 시뮬 → 기록 → 피로·부상 판정)
   → 매일 끝: 피로 회복 + 폼 변화
   → 주 결산: 부상 주차 감소·복귀, 2군 추정 성적, 알림, 하이라이트
```

**라인업은 매일 다시 짠다.** 화요일에 다친 선수가 수요일에 나오면 안 되고, 피로가 쌓인 포수는
규칙표의 휴식 기준에 걸려 저절로 빠져야 한다. 감독 AI 가 매일 현재 상태로 규칙표를 다시 만든다.

**(2) 피로는 투수와 야수를 따로 계산한다**

처음엔 하나의 회복 속도를 썼는데, 그러면 **야수가 영원히 지치지 않는다.** 투수는 한 경기에 75점씩
쌓이고(100구 × 0.75) 야수는 7점씩 쌓이는데, 투수 기준으로 회복 속도를 잡으면 야수의 피로가 매일
싹 지워지기 때문이다. 그래서 회복 속도를 분리했다.

| | 쌓임 | 회복(출장일/휴식일) | 결과 |
|---|---|---|---|
| 투수 | 투구수 × 0.75, 연투 +9, 3연투 +20 | 19 / 24 | 100구 선발은 4일이면 회복, 20구 불펜은 하루 |
| 야수 | 경기당 7 (포수 ×1.8) | 6 / 16 | 일반 야수는 거의 안 지치고, 포수는 2~3주에 한 번 쉰다 |

실제로 6주를 돌려 보면 포수 평균 피로가 다른 야수보다 확실히 높다(테스트로 고정).

**(3) 부상: 확률식과 영구 하락 (docs/08)**

```
부상 확률 = 기본(0.22%) × 피로 보정(최대 2.4배) × 내구도 보정 × 나이 보정(30세+ 매년 7%) × 팀 닥터 보정
```
부위는 투수·야수별 표에서 뽑고, **부위마다 떨어지는 능력치가 다르다** (햄스트링 → 주루,
팔꿈치 → 구위·제구, 손목 → 컨택·파워). 중상은 50% 확률로 1~4점, 시즌 아웃급은 반드시 3~8점
영구 하락하고 **잠재력 상한까지 함께 내려간다.** 복귀 후에는 재발 위험 기간(3주)이 붙어
그동안 부상 확률이 1.8배가 된다.

**(4) 폼: 랜덤 워크 + 평균 회귀**

매일 `폼 += (50 − 폼) × 0.18 + 정규분포(0, 기복에 비례한 폭)`. 기복(숨김 수치)이 큰 선수는
오르내림이 심하다. 2군에 내려가면 평균 쪽으로 60% 당겨진다 — "슬럼프 탈출을 위한 말소"가
실제로 의미 있게 만들기 위해서다 (docs/08).

**(5) 엔트리 (docs/07)**

순서가 중요하다: ① 부상자·복무자를 내리고 ② 재활을 마친 선수를 올리고 ③ 남은 자리를 2군 최고
선수로 채운다. 채울 때 **투수 10명·야수 14명**을 먼저 맞춘다 — 한 주 사이에 부상이 두세 명 나와도
라인업 9명이 무너지지 않게 여유를 두는 것이다. 말소한 선수는 다음 주에 못 올리고 그다음 주부터
가능하며(임시 규정), 부상자는 2군 재활 1주를 채워야 한다.

**(6) 2군은 시뮬레이션하지 않는다**

600명 가까운 2군 선수의 경기를 매주 돌리면 연산이 수십 배가 되는데, 2군 기록은 "누구를 올릴까"를
정하는 참고 자료다. 그래서 선수마다 한 주치 기대 성적을 능력치로 계산하고 랜덤 편차를 얹는다.
상대 수준은 1군보다 6점 낮게 잡는다.

**(7) 문자 중계는 이벤트를 문장으로 바꾸기만 한다**

중계를 위해 경기를 다시 돌리지 않는다(불변 원칙 5). 조사는 M1 에서 만든 `Hangul` 로 이름 끝
받침을 보고 고른다 — "김민준이 홈런!", "이서우가 안타". 주간 결산 하이라이트도 같은 스트림에서
뽑기 때문에 관전 여부와 무관하게 경기 내용과 일치한다.

### 3. 1,000시즌 검증이 잡아낸 버그 3개

대량 검증은 이번에도 값을 했다. 셋 다 한두 시즌만 돌려서는 안 보이는 버그였다.

1. **1군이 53명까지 불어났다.** 엔트리 매니저가 선수를 승격할 때 작업 목록에서 그 선수를
   *제거*하고 있었다. 인원을 세는 기준 목록에서 사라지니 "아직 28명이 안 됐다"고 판단해 계속
   올렸다. 목록에서 빼는 대신 **바꿔 끼우도록** 고쳤다.
2. **대타로 2군 선수와 부상자가 나왔다.** 벤치 후보를 "선수단 전체 중 라인업에 없는 야수"로
   잡았는데, 선수단에는 2군 선수도 부상자도 들어 있다. 1군 등록 + 출전 가능한 야수만 남기도록 고쳤다.
3. **부상이 겹치면 경기를 시작하지 못했다** (`야수가 모자라 라인업을 짤 수 없다`). 한 주에 야수가
   여럿 다치면 1군 야수가 9명 밑으로 떨어졌다. 엔트리 쪽에 야수 최소 인원을 두고, 그래도 모자라면
   2군에서 급히 채우는 **비상 라인업 사다리**를 넣었다. 경기는 어떤 경우에도 멈추지 않는다.

### 4. 캘리브레이션 (100시즌)

- **시즌 아웃 부상 기간은 18~44주로 잡았다** (임시). docs/08 의 "투수 팔꿈치 수술은 1년+"을 반영해

## M5. 성장·노화·은퇴 + 30시즌 밸런스 (2026-09-20) — **프로토타입 완성**

### 1. 무엇을 만들었나

| 파일 | 내용 |
|---|---|

| `Growth.kt` | 월별·시즌 후 성장, 출장 경험 보정, 코치 재분배, 능력치 그룹 |
| `Awakening.kt` | 각성(잠재력 상승)과 급노쇠 |

### 2. 핵심 로직이 왜 그렇게 동작하나

**(1) 성장은 "잠재력과의 차이를 좁히는" 방식이다 (docs/09)**

매년 (잠재력 − 현재)의 20~35%를 좁힌다. 그래서 어릴 때는 쑥쑥 크다가 잠재력에 가까워질수록
느려진다. 그중 **40%는 시즌 중 월 1회씩**(25세 이하만, 24주를 6번으로 나눔), **60%는 시즌 후**에
반영한다. 시즌 중에 유망주가 눈에 띄게 크는 맛을 내기 위한 분배다.

능력치마다 속도가 다르다(`attributeGrowthSpeed`). 파워·제구는 빨리 늘고 주루는 거의 안 는다.
하락기에는 반대로 주루(×1.7)·수비(×1.4)가 먼저 무너지고 선구안(×0.25)·제구(×0.35)는 오래 간다.
**M1 리그 생성기가 현재 능력치를 역산할 때 쓴 곡선과 같은 값**이라, 생성된 선수와 자라난 선수가
같은 규칙 위에 있다.

**(2) 코치는 총량을 늘리지 않고 재분배한다**

집중 능력치 ×1.3, **같은 그룹의 나머지 ×0.9**. 좋은 코치를 모으면 전 능력치가 다 오르는 구조가
되지 않게 하는 장치다(docs/09). 배율 크기는 코치 등급에 비례해서 1등급 코치는 거의 차이가 없다.
야수는 타격코치와 수비·주루코치 둘의 영향을 받으므로 코치를 **그룹별로** 들고 있는다.
감독 전문 분야는 해당 그룹 +10%, 2군 감독은 25세 이하 전체에 보너스를 준다.

**(3) 출장 경험 보정 (25세 이하)**

1군 주전 ×1.2 / 2군 주전 ×1.0 / 1군 벤치 ×0.7 / 거의 못 뜀 ×0.5 / 상무 ×1.0 / 현역 ×0(+감각 하락).
분류는 **그 시즌 실제 출장 기록**으로 한다(타석·아웃 카운트 기준, `growth.playingTimeThresholds`).
그래서 "유망주를 1군에서 쓸 것인가, 2군에서 매일 뛰게 할 것인가"가 성장 속도로 이어진다.

**(4) 각성과 급노쇠는 드물게**

각성은 25세 이하에게 1.5%(대기만성형은 2.2배), **현재 능력치가 아니라 잠재력이 5~10 오른다.**
당장 강해지는 게 아니라 "더 클 수 있게" 되는 것이라 스카우트·육성 판단이 흔들린다.
급노쇠는 33세 이상에게 5.5%, 그해 하락 폭이 2.4배가 된다. 30시즌 동안 각성 133명 / 급노쇠 118명
(시즌당 4명 안팎)으로, 사건으로 느껴질 만큼만 나온다.

**(5) 스토브리그 파이프라인의 순서**

```
① 성장·노화 → ② 각성·급노쇠 → ③ 은퇴 → ④ 군 복무 → ⑤ 계약 → ⑥ 신인 유입 → ⑦ 컨디션 초기화
```
성장을 **은퇴보다 먼저** 하는 이유는, 그해 성장을 반영한 뒤에 은퇴를 판정해야
"마지막에 반등한 베테랑이 그대로 은퇴하는" 이상한 결과가 안 나오기 때문이다.

**(6) 은퇴 선수 → 코치**

나이·능력치·계약 여부로 은퇴 확률을 매긴다(32세부터 매년 5.5%씩, 계약 없으면 +18%,
29세 이상인데 종합 48 미만이면 +30%, 44세면 강제). 은퇴 선수 중 일부(종합 58 이상의 25%)는
**무직 코치 후보**가 되고, 성향은 선수 시절 가장 잘하던 능력치를 물려받는다 — 거포였던 타자는
장타 중심 타격코치가 된다(docs/09). 30시즌에 51명이 코치로 전향했다.

**(7) 신인 유입은 아직 드래프트가 아니다**

계약금도 없다. M6 에서 실제 드래프트가 이 자리를 대신한다. 엔진은 선수를 만들 수 없어서

  줄어들 부분이다.

## M10(앞당김). 데스크톱 화면 프로토타입 (2026-09-20)

M6~M9 보다 먼저 화면을 붙였다. 유저가 지금까지 만든 것(리그 생성 → 경기 → 주간 루프 → 성장·은퇴)을
**직접 만져 보고 판단하기 위해서**다. M6~M9 기능이 붙으면 화면(시장·스카우트·구단·커리어)도 함께 늘린다.

### 1. 무엇을 만들었나

**`app` 모듈 (Compose Multiplatform 1.12.0 + Kotlin 2.4.20)**

지금은 **데스크톱(JVM) 타깃만** 켰다. 맥에서 바로 창을 띄워 보기 위해서다. 화면 코드는 전부
`commonMain` 에 있어서 Android/iOS 타깃을 추가하면 그대로 돈다.

| 파일 | 내용 |
|---|---|
| `GameSession.kt` | 화면과 엔진 사이의 유일한 창구. 주 진행·조회·지시·스토브리그 |
| `App.kt` | 구단 선택 → 하단 탭 5개 (홈·로스터·기록실·지시·중계) |
| `ui/Theme.kt` | 다크 테마, 능력치 색 구분 |
| `ui/Components.kt` | 능력치 막대(범위 표시), 게이지, 칩, 섹션 카드 |
| `screen/TeamSelectScreen.kt` | 구단 선택 = 난이도 선택 (전력·연봉·운용 자금·지명권·구단주 목표) |
| `screen/HomeScreen.kt` | 성적, 진행 버튼, 알림함, 하이라이트, 이번 주 일정, 순위, 스토브리그 |

### 2. 화면을 붙이면서 확인된 것

**(1) 불변 원칙 1·4가 실제로 지켜진다**

화면 코드는 파일을 읽지 않는다 — `Main.kt`(jvmMain)가 읽어서 넘긴다. `commonMain` 화면 코드는
`:engine` 만 의존하고 도구 모듈(`:tools`)은 jvmMain 에만 있다.

선수 능력치는 **`ScoutingView` 를 거쳐서만** 화면에 들어온다. 우리 팀 선수는 정확한 값이,
타 팀 선수는 범위가 나온다. 숨김 수치(잠재력·내구도·기복)는 애초에 엔진 밖에서 읽히지 않으므로
화면이 실수로 노출할 방법이 없다. 테스트로도 고정했다 —
*"우리 팀은 정확한 값, 타 팀은 범위로 본다"*.

**(2) 엔진에 화면용 구멍 세 개를 냈다**

- `WeekReport.watched`: 유저 팀 경기의 이벤트 스트림을 남긴다(관전용). 지정하지 않으면 안 남기므로
  1,000시즌 검증 같은 대량 실행에서는 메모리를 쓰지 않는다.
- `SeasonState.managerTendencies`: 감독 성향을 팀별로 들고 있는다. 지금까지는 리그 데이터의 값을
  그대로 읽었는데, 단장 방침으로 성향이 **움직여야** 하므로 시즌 상태로 옮겼다.
- `SeasonState.gmDirections`: 단장이 내린 방침. 매주 시작할 때 반영률(0.5)만큼 감독 성향에 섞인다.
  화면에서 "번트 선호 100" 을 지시하면 한 번에 100 이 되지 않고 매주 절반씩 다가간다 (docs/06).

**(3) 시즌 → 스토브리그 → 다음 시즌이 화면에서 이어진다**

정규시즌 24주가 끝나면 홈 화면에 스토브리그 버튼이 나오고, 누르면 성장·노화·각성·은퇴·신인 유입이
처리되어 다음 시즌이 시작된다. 결과(은퇴 N · 신인 N · 각성 N · 급노쇠 N · 입대 N)는 카드로 보여준다.

### 3. 테스트

```
./gradlew build → BUILD SUCCESSFUL, 경고 0, 171 테스트 통과 (app 9개 추가)
```
화면 자체는 눈으로 보는 게 빠르지만, **화면이 부르는 함수가 터지지 않는지**는 테스트로 잡았다:
주 진행과 조회, 기록실 순위, 정보 은닉(우리 팀/타 팀), 관전용 이벤트와 중계 문장,
주간 방침·단장 방침 반영, 시즌 끝까지 자동 진행, 스토브리그 후 다음 시즌 진행, 부상 선수 표시.

### 6. 임시 결정

- **데스크톱 타깃만 켰다.** Android/iOS 는 같은 `commonMain` 화면을 쓰되, 각 플랫폼 진입점에서
  리그 데이터를 읽어 `App()` 에 넘기면 된다. 안드로이드는 에셋에서, iOS 는 번들에서 읽게 된다.
- **엔트리 관리(등록·말소)는 아직 화면에서 못 한다.** AI 규칙이 자동으로 처리한다. M10 정식 작업에서
  로스터 화면에 올리기/내리기를 붙인다.
- **창 크기를 430×900 으로 고정**해 모바일 화면 비율로 맞췄다.
